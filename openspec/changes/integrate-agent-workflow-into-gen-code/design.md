## Context

当前后端 `chatToGenCode` 已承载 AI 代码生成主入口，但工作流能力与现有服务链路尚未完成标准化集成。现状存在四个问题：
1. 无统一路由开关，无法按请求决定是否走 Agent 工作流。
2. 工作流内部使用固定 `appId`，与业务应用上下文脱节。
3. 工作流未区分“首次创建应用”和“应用创建后的会话式修改”，导致用户发出局部改动指令（如“标题改为xxx”）时仍执行了不必要的图片收集与提示词增强步骤。
4. 工作流执行过程缺少完整会话留痕，不利于问题排查和持续优化。

该变更涉及 Controller、Service、Workflow、数据持久化与测试链路，属于跨模块集成改造。

## Goals / Non-Goals

**Goals:**
- 在不破坏现有默认行为的前提下，为 `chatToGenCode` 增加 `isAgent` 路由能力。
- 将业务 `appId` 透传到工作流执行上下文并在节点中可用。
- 让工作流按操作类型分支：首次创建模式全流程执行，会话式修改模式跳过图片相关与提示词增强节点。
- 在工作流请求、响应关键节点持久化用户对话记录，保证同一 `appId` 会话可追踪。
- 为上述行为补齐可回归测试。

**Non-Goals:**
- 不重构整个工作流编排框架。
- 不调整前端交互协议以外的页面逻辑。
- 不引入新的第三方消息中间件或事件总线。
- 不在本次变更中重做历史对话数据迁移。

## Decisions

1. 接口扩展方式：在现有请求 DTO 增加可选字段 `isAgent`（默认 `false`）。
- Rationale: 保持接口向后兼容，现有调用方无需立即改造。
- Alternative: 新增独立 Agent 接口。缺点是能力分叉、维护成本高。

2. 工作流上下文统一携带 `appId` 与 `operationType`，其中 `operationType` 由后端自动判定（根据应用是否已创建及用户指令语义）。
- Rationale: 调用方无需新增复杂参数，且能准确识别“首次创建”与“创建后局部修改”。
- Alternative: 由前端显式传 `operationType`。缺点是协议复杂、前端判定不可靠。

3. 场景分支使用工作流内条件节点而非外层硬编码跳步。
- Rationale: 行为定义集中在工作流图上，便于可视化维护与后续扩展。
- Alternative: 在 Service 层写 if/else 控制节点调用。缺点是流程定义分散。

4. 对话留痕采用“请求入库 + 结果入库”的双阶段持久化策略。
- Rationale: 即使中途失败也能保留用户输入，便于问题追踪。
- Alternative: 仅成功后一次性入库。缺点是失败链路丢失。

5. 错误处理策略：工作流失败返回统一错误结构，并保留传统路径兜底能力（可配置开关）。
- Rationale: 降低上线风险，支持灰度阶段快速回退。
- Alternative: 失败即直接透出异常。缺点是用户体验与稳定性不足。

## Risks / Trade-offs

- [Risk] `isAgent` 默认值处理不一致导致路由偏差 → Mitigation: 在 DTO、Service、测试三层统一默认行为断言。
- [Risk] `appId` 透传遗漏导致工作流写入错误上下文 → Mitigation: 增加参数校验与关键日志字段（traceId/appId）。
- [Risk] 会话式修改意图识别错误导致走错分支 → Mitigation: 引入可回归的意图判定规则与样例（包含“标题改为xxx”等高频编辑指令）。
- [Risk] 对话双写增加数据库压力 → Mitigation: 仅保留必要字段并支持异步化演进。

## Migration Plan

1. 数据层预检查：确认对话记录表结构满足新增字段（`appId`、角色、内容、时间、请求标识）。
2. 后端发布第一阶段：上线 `isAgent` 字段与服务路由，但默认关闭 Agent 路径。
3. 后端发布第二阶段：按应用或租户灰度打开 Agent 路由，监控成功率与时延。
4. 稳定后默认启用 Agent（按策略），保留配置开关用于快速回退。
5. 回滚策略：关闭 Agent 开关后全部回到传统路径，不影响接口兼容。
