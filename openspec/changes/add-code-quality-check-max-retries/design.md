## Context

当前工作流包含代码生成、质量检查、修复再检查等环节。`CodeQualityCheckerNode` 负责生成质量结果，但缺少统一的重试上限策略；当下游路由基于“不通过则继续修复并回到检查”时，存在无限循环风险。
本次变更需要在现有工作流状态中引入可计数、可判断、可观测的重试控制，且不影响质量检查通过时的正常主流程。

## Goals / Non-Goals

**Goals:**
- 为代码质量检查流程提供明确的最大重试次数控制，确保流程在异常或持续失败时可终止。
- 将重试次数与上限纳入 `WorkflowContext`，使节点与路由判断可读取同一事实来源。
- 在达到重试上限时输出可观测状态（结果字段 + 日志），便于排查与告警。

**Non-Goals:**
- 不改变 AI 质量检查本身的判分策略与提示词。
- 不引入新的外部依赖或持久化存储。
- 不重构整个 LangGraph 工作流，仅补齐重试边界行为。

## Decisions

1. 在 `WorkflowContext` 中新增并维护重试计数字段
- 方案：新增 `codeQualityRetryCount` 和 `codeQualityMaxRetries`（或等价字段），由质量检查与路由逻辑共同使用。
- 原因：状态集中管理可避免不同节点各自计数导致的不一致。
- 备选方案：仅在节点内用局部变量计数。
  - 放弃原因：节点是无状态执行，局部变量无法跨轮次保存。

2. 采用“失败后递增，达到上限立即终止流程”的策略
- 方案：质量检查失败时递增重试次数；路由阶段判断 `retryCount >= maxRetries` 时直接结束流程，不再回到修复循环。
- 原因：判断规则清晰，边界可测试，且完全避免死循环。
- 备选方案：达到上限后进入降级或人工介入分支。
  - 放弃原因：当前需求明确为达到上限后直接结束流程。

3. 最大重试次数默认值统一为 2，并允许覆盖
- 方案：系统默认 `codeQualityMaxRetries = 2`，允许通过上下文初始化或配置覆盖。
- 原因：默认值更保守，可更快止损；同时保留可配置性以兼容复杂任务。
- 备选方案：默认值设为 3。
  - 放弃原因：与当前产品决策不一致。

4. 达到上限时显式标记失败原因为“重试耗尽”
- 方案：在 `QualityResult` 错误列表或上下文字段中记录“达到最大重试次数”，并打印结构化日志（含当前计数和上限）。
- 原因：与普通质量不通过区分，便于监控与定位。
- 备选方案：仅输出日志，不修改结果对象。
  - 放弃原因：下游节点难以基于状态做可预测处理。

## Risks / Trade-offs

- [Risk] 现有路由条件与新计数语义不一致，可能提前终止或多跑一次  
  → Mitigation: 明确“失败后递增”的统一语义，并补充边界测试（0、1、2、3）。
- [Risk] 默认上限为 2 在复杂项目中可能过早终止  
  → Mitigation: 保持可配置并记录日志，后续按运行数据调整覆盖值。
- [Risk] 旧流程依赖“无限重试直到成功”行为  
  → Mitigation: 在变更说明中标注行为改变，并提供清晰的失败原因反馈。

## Migration Plan

1. 扩展 `WorkflowContext` 字段与初始化逻辑，保证旧请求在未显式配置时使用默认上限 2。  
2. 调整 `CodeQualityCheckerNode` 及相关路由判断，接入计数递增与上限终止。  
3. 增加/更新单元测试覆盖边界情况。  
4. 灰度运行观察日志中的“重试耗尽”比例，必要时通过配置覆盖默认值。
